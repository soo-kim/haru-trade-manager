# PRD: 한국 주식 자동매매 시그널 시스템

> **버전:** 0.1 (기획 초안)  
> **작성일:** 2026-03-31  
> **상태:** 검토 중

-----

## 1. 개요

### 1.1 목적

키움증권 REST API를 기반으로, 코스피/코스닥 주식 시장에서 다중 전략 시그널을 자동 생성하고 자동 주문까지 실행하는 시스템을 구축한다. 백테스트 무결성을 최우선으로 설계하여 과거 성과가 실전 성과로 이어지도록 한다.

### 1.2 핵심 설계 원칙

- **백테스트 무결성**: 신호 생성봉과 진입봉을 구조적으로 분리. 수수료 + 슬리피지 강제 반영.
- **리스크 우선**: 수익보다 손실 제한이 항상 우선한다.
- **단계적 실전 투입**: 페이퍼 트레이딩 → 소액 실계좌 → 점진적 증액.
- **운영 유연성**: 텔레그램 명령으로 핵심 파라미터를 실시간 변경 가능.

## 2. 시스템 범위

### 2.1 대상 시장

|구분       |내용                                |
|---------|----------------------------------|
|정규장      |코스피 / 코스닥, 09:00 ~ 15:30          |
|NXT 프리마켓 |넥스트레이드, 08:00 ~ 09:00             |
|NXT 애프터마켓|넥스트레이드, 15:30 ~ 20:00             |
|제외       |동시호가 구간 (08:30~09:00, 15:20~15:30)|

### 2.2 종목 유니버스

유니버스는 두 계층으로 구분한다.

|계층         |범위                       |역할                                            |
|-----------|-------------------------|----------------------------------------------|
|**전체 유니버스**|코스피200 + 코스닥150 (약 350종목)|히스토리 데이터 수집 및 유지 대상. 유동성 조건과 무관하게 항상 최신 데이터 보관|
|**활성 유니버스**|전체 유니버스 중 유동성 필터 통과 종목   |전략 스크리닝 및 매수 시그널 발생 대상                        |


> **분리 이유:** 오늘 유동성 필터에서 탈락한 종목이 내일 재편입될 수 있다. 데이터가 없으면 재편입 즉시 전략 대상이 될 수 없고, 백테스트에서 과거 특정 시점의 유동성 필터를 재현하려면 해당 시점 데이터가 필요하다.

#### 유동성 필터 (활성 유니버스 기준)

- 기준: 최근 20일 평균 거래대금 ≥ 50억 원
- 갱신: 루프 C(30분 주기)에서 재계산
- 거래 정지 / 관리 종목 / 투자 경고 종목은 활성 유니버스에서 즉시 제외
- 필터 기준은 텔레그램 명령으로 변경 가능 (`/set liquidity 50`)

#### 활성 유니버스 이탈 시 보유 포지션 처리

- 이탈 종목에 보유 포지션이 있으면 “이탈 예정” 상태로 표시
- 신규 진입은 차단하고, 기존 포지션은 정상 손절/익절 로직으로 관리 후 청산 시 활성 유니버스에서 제거
- 전체 유니버스(데이터 수집)에서는 제거하지 않음

#### 전체 유니버스 리밸런싱 주기

- **자동:** 매월 1일 자정에 코스피200 / 코스닥150 구성 종목을 조회하여 전체 유니버스를 갱신
- **수동:** 웹 대시보드에서 즉시 실행 가능
- 리밸런싱 결과(편입/제외 종목 목록)는 텔레그램으로 발송

#### 전체 유니버스 변경 처리

코스피200 / 코스닥150 구성 종목이 변경될 때만 전체 유니버스가 바뀐다.

```
리밸런싱 실행 (매월 1일 자정 or 수동)
  ↓
신규 편입 종목 감지
  ↓
히스토리 배치 수집 시작 (백그라운드, 최하위 우선순위)
  - 일봉: 5년 / 60분봉: 2년 / 15분봉: 6개월 / 5분봉: 6개월
  ↓
전략별 최소 데이터 요구량 충족 확인
  ↓
충족 → 활성 유니버스 편입 후보 등록 (유동성 필터 통과 시 활성화)
미충족 → 다음 루프 C에서 재확인

제외 종목 감지
  ↓
보유 포지션 없음 → 전체 유니버스에서 즉시 제거
보유 포지션 있음 → "이탈 예정" 상태로 표시, 청산 후 제거
```

#### 블록 리스트 (Block List)

지수 편입 종목이더라도 매매를 원하지 않는 종목을 관리하는 목록. 데이터 수집은 계속 유지하되, 활성 유니버스에서만 제외하여 매수 시그널 발생을 차단한다. 블록 해제 시 유동성 필터 통과 여부에 따라 즉시 활성 유니버스에 복귀.

- 관리: 웹 대시보드 또는 텔레그램 명령
- 블록 리스트 추가 시 보유 포지션이 있으면 즉시 제거하지 않고 **“이탈 예정”** 상태로 전환. 정상 손절/익절 로직으로 청산 후 활성 유니버스에서 제거
- 블록 리스트는 DB에 영구 저장. 리밸런싱 후에도 유지됨

## 3. 데이터 수집 전략

### 3.1 수집 범위 (계층별)

|타임프레임|수집 기간        |용도                   |
|-----|-------------|---------------------|
|일봉   |5년 (약 1,250봉)|지지/저항, 추세 판단, 백테스트 기반|
|주봉   |5년           |장기 추세 확인             |
|60분봉 |2년           |중기 전략 신호             |
|15분봉 |6개월          |진입 타이밍               |
|5분봉  |6개월          |실시간 체결 모니터링          |


> **키움 API 한계 대응:** 일봉은 최대 600봉 단위로 분할 호출. 초기 수집 시 배치 작업으로 처리. 이후 매일 증분 업데이트.

### 3.2 데이터 저장 및 증분 업데이트

- DB: PostgreSQL
- 생존자 편향 제거: 상장폐지 종목 이력도 별도 테이블로 보관 (백테스트 정확도용)

#### 캔들 수집 전략

**초기 수집 (히스토리 배치):** 종목 최초 등록 시 타임프레임별 전체 기간을 대량 INSERT.

**증분 업데이트 (루프 B, 봉 마감 시):**

```
DB에서 해당 종목/타임프레임의 마지막 봉 기준시각 조회
  ↓
API 요청: 마지막 봉 기준시각 이후 데이터
  ↓
마지막 봉과 동일한 기준시각의 봉 → UPDATE
  (장중에는 마지막 봉이 아직 진행 중일 수 있어 데이터가 변경됨)
그 이후 신규 봉 → INSERT
```

이 방식은 UPSERT(전체 PK 충돌 검사)를 피하고 마지막 봉 1건만 UPDATE하므로 DB 부하를 최소화한다. 키움 API가 반환하는 최대 봉 수(일봉 600개, 분봉 900개)를 매번 처리하지 않고 실제 변경분만 처리한다.

## 4. 전략 레이어

### 4.1 전략 구조 — 인스턴스 기반 설계

각 전략은 클래스로 구현하고, **초기화 시 타임프레임과 활성 시간대를 파라미터로 주입**한다. 루프 B는 봉이 마감될 때마다 해당 타임프레임을 사용하는 인스턴스만 호출하고, 인스턴스는 자신의 활성 시간대 여부를 내부에서 판단한다.

```python
# 인스턴스 생성 예시 (시스템 시작 시 일괄 초기화)
strategies = [
    GapMomentum(timeframe="5m",  active_hours=[("08:00","09:00"), ("09:00","09:30")]),
    EmaPullback(timeframe="15m", active_hours=[("09:00","15:20")]),
    VolatilityBreakout(timeframe="5m",  active_hours=[("09:00","15:20")]),
    VolumeSurge(timeframe="5m",  active_hours=[("09:00","15:20"), ("15:30","20:00")]),
    SupportResistance(timeframe="15m", active_hours=[("09:00","15:20")]),
]
```

루프 B는 봉 마감 시 해당 타임프레임을 가진 인스턴스 목록만 필터링하여 스크리닝을 실행한다. 인스턴스를 추가하거나 타임프레임/시간대를 바꾸는 것으로 전략 구성을 유연하게 조정할 수 있다.

```
루프 B — 봉 마감 감지 (예: 5분봉 마감)
  ↓
timeframe == "5m" 인 전략 인스턴스 필터링
  → GapMomentum, VolatilityBreakout, VolumeSurge
  ↓
각 인스턴스 호출
  → 인스턴스 내부에서 현재 시각이 active_hours 범위인지 확인
  → 범위 밖이면 스크리닝 스킵
  → 범위 안이면 전략 로직 실행 → 시그널 생성
```

### 4.2 전략 목록 (5개)

#### 전략 1 — 갭 모멘텀

- **조건:** 시가 갭 ±2% 이상 발생 시 방향 추종
- **필터:** 갭 구간에 전일 거래량 공백 없을 것 (허수 갭 제거)
- **기본 타임프레임:** 5분봉
- **기본 활성 시간대:** NXT 프리마켓 08:00~09:00, 정규장 시초 09:00~09:30
- **NXT 적용 시 포지션:** 정규장의 50%

#### 전략 2 — EMA 눌림목

- **조건:** 5/20/60 EMA 정배열 → 20EMA 단기 눌림 → 거래량 동반 반등
- **기본 타임프레임:** 15분봉
- **기본 활성 시간대:** 정규장 09:00~15:20
- **특징:** 추세 국면에서 가장 안정적

#### 전략 3 — 변동성 돌파

- **조건:** 전일 고가 + (전일 고가 - 전일 저가) × K 돌파 (기본 K=0.5)
- **출처:** 래리 윌리엄스 방식 변형
- **파라미터 K:** 백테스트 결과에 따라 자동 최적화
- **기본 타임프레임:** 5분봉
- **기본 활성 시간대:** 정규장 09:00~15:20

#### 전략 4 — 거래량 급증 모멘텀

- **조건:** 직전 20봉 평균 거래량 대비 3배 이상 + 가격 1% 이상 상승 동반
- **기본 타임프레임:** 5분봉
- **기본 활성 시간대:** 정규장 09:00~15:20, NXT 애프터마켓 15:30~20:00 (유일하게 애프터에서도 허용)
- **오버나이트 허용:** 15:20 미수 강제 청산 로직에서 전략4 포지션은 가장 마지막 청산 순번으로 설정(기본값). 계좌 전체 포지션이 자기 자금 이하로 내려오면 전략4 포지션은 청산 없이 오버나이트 유지. 다음 날 장 시작 전 루틴(07:50)에서 모니터링 재개.

#### 전략 5 — 지지/저항 반등·돌파

- **지지/저항 산출 방식:**
  - **피봇 포인트:** 전일 고/저/종가로 당일 레벨 계산 (단순, 안정적)
  - **프라이스 클러스터링:** 과거 N봉에서 가격 밀집 구간 탐지 (동적 레벨)
  - 두 방식 모두 적용, 겹치는 레벨은 강도 상향
- **진입:**
  - 지지 레벨 근처에서 거래량 동반 반등 → 매수
  - 저항 레벨 상향 돌파 + 거래량 확인 → 매수
- **기본 타임프레임:** 15분봉
- **기본 활성 시간대:** 정규장 09:00~15:20

### 4.3 전략 성과 추적

- 전략별 승률, 손익비, 기대값을 실시간 업데이트
- 성과 부진 전략은 가중치 자동 하향 (완전 비활성화는 하지 않음)
- 가중치 변경 시 텔레그램으로 알림

### 4.4 진입/청산 구조

#### 주문 유형

|상황                      |주문 유형           |이유                                                         |
|------------------------|----------------|-----------------------------------------------------------|
|진입                      |지정가 (허용 범위 0.3%)|슬리피지 통제. `order_cancel_minutes` 경과 후에도 미체결이면 주문 취소 후 시그널 포기|
|1단계 익절                  |시장가 (폴링 감지 즉시)  |지정가 미체결 문제 제거. 익절가 터치 시 즉시 체결                              |
|손절                      |시장가             |빠른 이탈 최우선                                                  |
|트레일링 스탑 청산              |시장가             |빠른 이탈 최우선                                                  |
|강제 청산 (미수 15:20, 시스템 정지)|시장가             |빠른 이탈 최우선                                                  |


> **미체결 주문 자동 취소 흐름:**
> 
> ```
> 진입 지정가 주문 전송
>   ↓
> 루프 A 매 턴마다 미체결 여부 확인
>   ↓
> 주문 경과 시간 ≥ order_cancel_minutes?
>   Yes → 키움 API로 주문 취소 요청 → 취소 확인 → 로그 기록
>   No  → 계속 대기
> ```

> **익절 감지 흐름:**
> 
> ```
> 루프 A 폴링 → 현재가 ≥ 익절가 감지
>   ↓
> 시장가로 절반 즉시 매도
>   ↓
> 체결 완료 → HALF_CLOSED, 트레일링 스탑 시작
> 체결 실패 → 1회 재시도 → 실패 시 텔레그램 알림 + 수동 처리
> ```

#### 진입

전량 일괄 매수. 분할 매수 없음.

#### 손절

진입 시점 ATR을 기록하고 고정 손절가를 설정. 이후 변경 없음.

```
손절가 = 진입가 - (ATR × stop_atr_mult)
```

#### 청산 2단계

**1단계 — 고정 익절 (보유 수량의 50%)**

```
익절가 = 진입가 + (ATR × tp_atr_mult)
```

폴링으로 익절가 도달 감지 후 시장가로 즉시 절반 청산. 포지션 상태를 `HALF_CLOSED`로 전환.

**2단계 — 트레일링 스탑 (잔여 50%)**

1단계 익절 완료 후 고점을 추적하며 트레일링 스탑가를 갱신.

```
트레일링 스탑가 = 갱신된 고점 - (ATR × trail_atr_mult)
```

현재가가 트레일링 스탑가를 하향 돌파 시 잔여 전량 시장가 청산. 포지션 상태 `CLOSED`.

> **15:20 미수 강제 청산 루틴:** 미수 사용 설정 여부와 무관하게 매일 15:20에 아래 루틴을 실행한다. 장중에 진입/청산이 반복되면서 전체 포지션 규모가 자기 자금 이하로 자연 해소될 수 있으므로, 포지션 단위가 아닌 **계좌 전체 레벨**에서 미수 잔존 여부를 판단한다.
> 
> ```
> 15:20 도달
>   ↓
> 전체 보유 포지션 평가금액 합산
>   ↓
> 합산 ≤ daily_base_capital?
>   Yes → 미수 없음. 아무것도 하지 않음.
>   No  → 미수 잔존. 강제 청산 루틴 시작
>           ↓
>         margin_close_priority 순서대로 포지션 목록 정렬
>           ↓
>         순서대로 포지션 1개씩 시장가 전량 청산
>           ↓
>         청산 후 전체 포지션 평가금액 재계산
>           ↓
>         아직 > daily_base_capital? → 다음 포지션 청산 반복
>         ≤ daily_base_capital?    → 중단 (이후 포지션 유지)
> ```
> 
> **청산 순번 설정 (`margin_close_priority`):** 전략 ID 목록을 순서대로 나열. 앞 번호부터 먼저 청산. 기본값은 `[1, 2, 3, 5, 4]`로, 전략4(거래량 급증)가 가장 마지막이므로 미수가 해소되는 시점까지 전략4 포지션은 청산되지 않는다. 설정 변경은 웹UI에서만 가능.
> 
> **백테스트 보수 처리:** 같은 봉에서 고점 갱신과 스탑 터치가 동시 발생하는 경우, 스탑이 먼저 터진 것으로 처리.

#### 포지션 상태머신

|상태           |설명                    |
|-------------|----------------------|
|`OPEN`       |진입 완료. 1단계 익절 및 손절 대기 |
|`HALF_CLOSED`|절반 익절 완료. 트레일링 스탑 진행 중|
|`CLOSED`     |전량 청산 완료              |

고점 및 현재 트레일링 스탑가는 DB에 저장. 시스템 재시작 후에도 상태 복원 가능.

#### 전략별 독립 포지션

동일 종목에 복수 전략이 동시에 시그널을 내면 각 전략별로 독립적인 포지션을 진입한다. 포지션 한도, 수량, 손절/익절 파라미터가 전략별로 완전히 분리된다.

```
예시: 종목 A에 전략2(EMA 눌림목)와 전략5(지지/저항)가 동시 시그널
  → 전략2 포지션: 독립 진입, 전략2 파라미터로 손절/익절
  → 전략5 포지션: 독립 진입, 전략5 파라미터로 손절/익절
  → 종목 A 합산 비중 = 전략2 비중 + 전략5 비중 (중복 허용)
```

> **중복 시그널 = 강한 신호:** 복수 전략이 같은 종목을 동시에 포착했다는 것은 그만큼 신호 강도가 높다고 해석한다. 합산 비중이 높아지는 것을 허용.
> 
> **청산 독립성 보장:** 각 전략 포지션은 자신의 수량만큼만 익절/손절. 다른 전략 포지션에 영향 없음. `/close [종목코드]` 명령 실행 시 해당 종목의 전체 전략 포지션을 모두 청산.

#### 청산 파라미터

공통 기본값을 두고 전략별로 오버라이드 가능. ConfigManager에서 관리. 루프 C의 파라미터 재최적화 대상에 포함.

|파라미터            |설명             |공통 기본값|
|----------------|---------------|------|
|`atr_period`    |ATR 계산 기간 (봉 수)|14    |
|`stop_atr_mult` |손절 ATR 배수      |1.5   |
|`tp_atr_mult`   |1단계 익절 ATR 배수  |2.0   |
|`trail_atr_mult`|트레일링 스탑 ATR 배수 |1.5   |

전략별 오버라이드 예시:

|전략     |특성               |오버라이드 예시             |
|-------|-----------------|---------------------|
|갭 모멘텀  |빠른 단타, 타이트한 기준   |`stop=1.0`, `tp=1.5` |
|EMA 눌림목|추세 추종, 여유 있는 트레일링|`trail=2.0`          |
|변동성 돌파 |돌파 후 급등 기대       |`tp=2.5`, `trail=2.0`|
|거래량 급증 |단기 급등, 빠른 익절     |`stop=1.0`, `tp=1.5` |
|지지/저항  |레벨 기반, 명확한 손절    |`stop=1.2`           |

## 5. 브레인 파이프라인

### 5.1 REST 단일 클라이언트 (RateLimitedClient)

모든 REST 요청은 싱글턴 클라이언트 하나가 순차 처리한다. 모든 루프가 이 클라이언트를 공유하며, 어떤 모듈도 직접 HTTP 호출을 하지 않는다. 인증 토큰 관리도 이 클라이언트가 담당한다.

```
RateLimitedClient (싱글턴)
  - last_request_time 보유
  - 요청 전 경과 시간 < 0.2초이면 자동 대기
  - 내부 Lock으로 동시 접근 차단
  - 우선순위 큐: 주문 요청 > 데이터 수집 요청
  - 액세스 토큰 및 만료 시각 보유
```

#### 인증 세션 관리

모든 요청 실행 전 토큰 유효성을 확인한다. 만료 후 갱신이 아닌 **만료 전 선제 갱신**이 원칙. 토큰이 만료된 상태에서 손절 주문이 실행되는 상황을 구조적으로 방지한다.

```
요청 실행 전
  ↓
토큰 만료까지 5분 이하?
  ↓
Yes → 백그라운드 토큰 갱신 (요청 블로킹 없이)
No → 그대로 진행

토큰 갱신 실패 시
  ↓
재시도 3회 (1s → 2s → 4s 지수 백오프)
  ↓
모두 실패 → 시스템 정지 + 텔레그램 긴급 알림
  (인증 실패는 API 연결 오류와 동일하게 처리)
```

> **시스템 시작 시:** 저장된 토큰이 있으면 유효성 확인 후 재사용. 없거나 만료 시 즉시 신규 발급.
> 
> **토큰은 DB에 저장.** 컨테이너 재시작 시 재인증 없이 복원 가능.

> **우선순위 큐 이유:** 루프 B의 캔들 수집이 API를 점유하는 동안 루프 A의 손절 주문이 밀리는 상황 방지.

### 5.2 세 가지 루프 구조

#### 루프 A — 보유 종목 실시간 모니터링 + 시그널 주문 실행 (무한루프)

두 가지 역할을 담당한다: (1) 보유 종목 손절/익절 감시, (2) 루프 B가 생성한 시그널 큐 소비 후 즉시 주문 실행.

```
매 턴:
  ① 시그널 큐 확인
      큐에 시그널 있음 → 리스크 최종 확인 후 즉시 주문 실행
                         체결 확인 → 포지션 DB 업데이트 + 텔레그램 알림
  ↓
  ② 보유 종목 현재가 수집 (RateLimitedClient)
      (보유 종목 없으면 ①만 반복)
  ↓
  ③ 손절 / 익절 / 트레일링 스탑 조건 체크
  ↓
  ④ 조건 충족 시 즉시 주문 → 체결 확인
  ↓
  ⑤ 포지션 상태 DB 업데이트 + 텔레그램 알림
```

> **웹소켓 전환 포인트:** 이 루프의 ② 현재가 폴링만 나중에 웹소켓으로 교체하면 실시간성을 높일 수 있음. 루프 B/C와 분리되어 있어 전환 범위 최소화 가능.

#### 루프 B — 캔들 업데이트 + 전략 실행 (무한루프, 시각 체크)

봉 마감 시각을 무한루프로 체크하다가 마감 시점에 캔들을 수집하고, **마감된 N봉 데이터를 기반으로 시그널을 생성**한다. 생성된 시그널은 공유 큐에 적재되고 루프 A가 소비하여 즉시 주문을 실행한다.

봉 마감 시각은 장 시작(09:00)과 NXT 시작(08:00)을 각각 기준점으로 계산한다. **봉 마감 시각 체크는 반드시 증권사 서버 시간 기준으로 수행한다.** (시간 동기화 방식은 아래 참고)

```
현재 시각 확인 (증권사 서버 시간 기준 offset 적용)
  ↓
봉 마감 시각 해당 여부 체크
  (미해당이면 루프 재시작)
  ↓
해당 타임프레임 캔들 수집 (순차 처리)
  5분 단위 마감 → 5분봉
  15분 단위 마감 → 5분봉 + 15분봉
  정각 마감     → 5분봉 + 15분봉 + 1시간봉
  장 마감(15:30) → 일봉
  NXT 마감(20:00) → NXT 전용 처리
  ↓
마감된 N봉 기준으로 전략 인스턴스별 스크리닝
  ↓
시그널 생성 → 리스크 체크
  ↓
통과 시 → 시그널 큐에 적재 (루프 A가 소비)
미통과 시 → 로그 기록 후 폐기
```

> **시그널 생성 타이밍:** 루프 B는 N봉이 마감되는 시점에 시그널을 생성한다. 실전에서 주문은 루프 A가 시그널 큐를 감지하는 즉시 실행하므로 실질적으로 N봉 마감 직후 시장가(또는 지정가)로 진입된다. 백테스트에서는 “N+1봉 시가”로 체결 시뮬레이션하여 무결성을 유지한다 (5.4절 참고).
> 
> **중복 수집 방지:** 별도 플래그 없이 봉의 기준 시각을 Primary Key로 저장. 동일 기준 시각의 봉이 이미 존재하면 INSERT를 건너뜀(UPSERT 방식).
> 
> **정각 몰림 대응:** 타임프레임 순서대로 순차 처리. RateLimitedClient의 0.2초 딜레이로 자연 분산.

#### 증권사 서버 시간 동기화

봉 마감 시각을 정확히 판단하려면 로컬 시계가 아닌 증권사 서버 기준 시각을 사용해야 한다.

```
시스템 시작 시 (장 시작 전 루틴 직전)
  ↓
키움 REST API에서 서버 현재 시각 조회
  ↓
server_time_offset = 서버시각 - 로컬시각  (초 단위, 음수 가능)
ConfigManager에 저장
  ↓
이후 모든 봉 마감 시각 체크는 (로컬시각 + offset)으로 수행
```

> **offset 재동기화:** 장 시작 전 루틴(07:50)에서 매일 1회 재측정. 운영 중 offset이 5초 이상 변동되면 경고 로그 기록.
> offset 조회가 실패하면 직전 저장값을 유지하고 텔레그램으로 경고 발송.

#### 루프 C — 유지보수 (30분 주기)

```
유니버스 필터 재계산 (거래대금 기준)
  ↓
전략 가중치 / 파라미터 재최적화
  ↓
일일 성과 집계 및 DB 기록
```

#### 장 시작 전 루틴 (매일 07:50, 별도 스케줄)

```
계좌 잔고 조회
  ↓
당일 기준 자산(daily_base_capital) 확정 → ConfigManager 저장 (읽기 전용)
  ↓
전략별 최대 포지션 금액 사전 계산
  = daily_base_capital × position_size_max_pct ÷ 100
  ↓
당일 장중 모든 포지션 사이징은 daily_base_capital 기준으로 고정
  ↓
계좌 스냅샷 기록 (snapshot_type: pre_market)
```

#### 계좌 스냅샷 (account_snapshots)

장 주요 시점마다 계좌 전체 상태를 DB에 기록한다. 입출금으로 자산 총액이 크게 변할 수 있으므로 스냅샷은 **실계좌 상태의 참고 기록 및 오차 감지용**으로만 사용한다. 성과 측정은 매매 기록 기반 직접 계산 방식을 사용한다.

|스냅샷 시점|snapshot_type |설명                                 |
|------|--------------|-----------------------------------|
|07:50 |`pre_market`  |기준 자산 확정 시점 (daily_base_capital 전용)|
|09:00 |`market_open` |정규장 시작 직전                          |
|15:30 |`market_close`|정규장 마감 직후                          |
|20:00 |`after_close` |NXT 마감 직후                          |

```
account_snapshots 테이블
  snapshot_time     스냅샷 시각
  snapshot_type     pre_market | market_open | market_close | after_close
  total_assets      총 자산 (현금 + 주식 평가금액)
  cash              현금 잔고
  stock_value       주식 평가금액
  margin_used       미수 사용금액
  open_positions    보유 포지션 수
```

#### 성과 측정 — 시간가중수익률 (TWR)

입출금이 있으면 단순 자산 증감으로는 성과를 올바르게 측정할 수 없다. 입출금 시점을 구간 경계로 분리하여 각 구간 수익률을 곱하는 **시간가중수익률(TWR)** 방식을 사용한다.

```
예시:
  1월 1일  자산 1,000만 원
  1월 15일 +5% 수익 → 1,050만 원
  1월 15일 500만 원 입금 → 1,550만 원  ← 구간 경계
  2월 1일  +2% 수익 → 1,581만 원

TWR = (1.05 × 1.02) - 1 = 7.1%   ← 입금 영향 제거된 실제 운용 수익률
단순 계산 = 58.1%                  ← 입금으로 왜곡된 수치
```

**입출금 감지 및 기록**

스냅샷 간 자산 변화에서 매매 손익으로 설명되지 않는 금액을 입출금으로 감지한다.

```
입출금 감지 (스냅샷 비교 시)
  ↓
입출금 = 자산 변화 - 해당 구간 매매 손익 합계
  ↓
일정 금액(기본 1만 원) 이상이면 cash_flows 테이블에 자동 기록
```

```
cash_flows 테이블
  flow_time       감지 시각
  amount          금액 (양수: 입금, 음수: 출금)
  total_before    입출금 전 자산
  total_after     입출금 후 자산
  detected_by     auto | manual  (배당금 등 자동 감지 누락분은 수동 입력)
```

**성과 지표 계산 기반**

|지표       |계산 기반                                       |
|---------|--------------------------------------------|
|수익률 (TWR)|매매 기록 + cash_flows 기반 구간 분리 계산              |
|에쿼티 커브   |매매 기록 기반 누적 손익                              |
|실계좌 오차 감지|계산값 vs 스냅샷 비교 (참고용)                         |
|기준 자산    |07:50 pre_market 스냅샷 (daily_base_capital 전용)|

### 5.3 오류 처리 설계

#### 일반 API 오류

|오류 유형          |처리 방식                            |
|---------------|---------------------------------|
|HTTP 4xx       |즉시 로그 + 텔레그램 알림, 재시도 안 함         |
|HTTP 5xx / 타임아웃|지수 백오프 최대 3회 재시도 (0.5s → 1s → 2s)|
|3회 재시도 실패      |해당 요청 포기, 텔레그램 경고 발송             |
|API 연결 오류 3회 연속|시스템 정지 + 텔레그램 긴급 알림              |

#### 주문 관련 오류 (일반 오류와 별도 처리)

주문은 서버 도달 여부가 불명확한 상태가 가장 위험하다. 아래 흐름을 반드시 따른다.

```
주문 요청 전송
  ↓
응답 수신 실패 또는 오류
  ↓
주문 상태 조회 (체결/미체결/없음 확인)
  ↓
미체결 확인 → 1회 재시도
주문 없음 확인 → 재주문
조회 자체 실패 → 포지션 불일치 경고 + 시스템 정지
```

> **포지션 불일치:** 시스템이 알고 있는 포지션과 실제 계좌 포지션이 다른 경우. 두 가지 처리 방식 중 선택 가능.
> 
> - **자동 싱크 모드 (기본):** 실제 계좌 포지션을 기준으로 시스템 내부 상태를 자동으로 동기화한 뒤 루프 재시작. 텔레그램으로 싱크 내용 발송.
> - **수동 확인 모드:** 시스템 정지 후 수동 확인 요청. `/resume` 명령으로만 재가동.
> - 모드 전환: `/set sync_mode auto | manual`

### 5.4 신호 생성 → 진입 분리 규칙 (백테스트 무결성 핵심)

실전과 백테스트는 진입 시점 처리가 다르다. 이 차이를 코드 레벨에서 구조적으로 분리하여 백테스트 과최적화를 방지한다.

|구분      |신호 생성   |진입 체결 기준                  |
|--------|--------|--------------------------|
|**실전**  |N봉 마감 시점|마감 직후 루프 A가 시장가/지정가로 즉시 주문|
|**백테스트**|N봉 종가 기준|N+1봉 시가로 체결 시뮬레이션         |

```
수수료: 매수 0.015% + 매도 0.015% + 증권거래세 0.18% (매도 시)
슬리피지: 기본 0.05% (텔레그램으로 조정 가능)
```

> 이 규칙은 코드 레벨에서 구조적으로 강제 적용. 우회 불가.

## 6. 설정 중앙 관리 (ConfigManager)

### 6.1 구조

모든 설정값은 싱글턴 ConfigManager 하나가 소유한다. 시스템 내 모든 모듈은 이 객체를 통해서만 설정값을 읽고 쓴다.

```
ConfigManager (싱글턴)
  - 메모리 내 설정값 보유
  - 읽기: get(key) → 메모리에서 즉시 반환
  - 쓰기: set(key, value) → 검증 → 메모리 갱신 → DB 저장 → 변경 이벤트 발행
```

**저장 계층**

```
메모리 (ConfigManager)  ←→  DB (config 테이블, Source of Truth)
```

시스템 시작 시 DB에서 전체 설정을 로드. 이후 변경은 메모리와 DB를 동시에 업데이트. 재시작 시 DB에서 복원하므로 설정값 유실 없음.

**즉시 반영 보장**

루프들은 설정값을 로컬 변수에 캐싱하지 않고, 매 사이클마다 ConfigManager에서 직접 읽는다. 이 원칙을 코드 레벨에서 강제한다.

**변경 검증**

설정값마다 허용 범위와 타입을 정의. 범위 초과 또는 타입 오류 시 즉시 거부하고 오류 메시지 반환.

**변경 이력**

모든 설정 변경은 `config_history` 테이블에 기록 (변경 시각, 변경 주체, 키, 이전값, 변경값). 웹 대시보드에서 이력 조회 가능.

#### 포지션 사이징 계산

ATR 기반으로 종목별 변동성을 반영하여 포지션 크기를 결정한다. 손실 금액을 일정하게 맞추는 방식.

**미수 허용 여부에 따라 포지션 크기의 기준이 달라진다.**

- `margin_ratio > 1.0` (미수 허용 상태): 미수 포함 실제 투입 가능 금액 기준
- `margin_ratio = 1.0` (미수 미사용): 자기 자금(daily_base_capital) 기준

```
[미수 미사용]
가용 자산 = daily_base_capital
1회 허용 손실 = 가용 자산 × risk_per_trade_pct
손절 폭(금액) = 진입가 × stop_atr_mult × ATR비율
포지션 크기  = 1회 허용 손실 ÷ 손절 폭

[미수 허용]
가용 자산 = daily_base_capital × margin_ratio
1회 허용 손실 = daily_base_capital × risk_per_trade_pct  ← 손실 기준은 자기자금 기준 유지
손절 폭(금액) = 진입가 × stop_atr_mult × ATR비율
포지션 크기  = 1회 허용 손실 ÷ 손절 폭
(단, 포지션 크기 상한 = 가용 자산 × position_size_max_pct)

→ position_size_min_pct 미달 시: 시그널 포기
→ position_size_max_pct 초과 시: 캡 적용
```

> **손실 기준은 항상 자기 자금 기준으로 고정.** 미수를 쓰더라도 `risk_per_trade_pct`가 뜻하는 “1회 허용 손실”은 레버리지 전 원금 대비 비율이다. 포지션 크기(투입 금액)만 미수 배율만큼 더 커질 수 있다.

예시 (총 자산 1,000만 원, risk_per_trade_pct=0.5%):

- 손절 폭 2% 종목 → 포지션 250만 원 (25%)이지만 캡 10% 적용 → 100만 원
- 손절 폭 5% 종목 → 포지션 100만 원 (10%) → 캡 그대로
- 손절 폭 25% 종목 → 포지션 20만 원 (2%) → 최소 한도 충족

`risk_per_trade_pct`가 핵심 레버. 텔레그램으로 장중 실시간 조정 가능.

|키             |기본값 |허용 범위  |설명         |
|--------------|----|-------|-----------|
|`slippage_pct`|0.05|0 ~ 0.5|슬리피지 가정 (%)|

## 7. 리스크 관리

### 7.1 시스템 자동 정지 조건 및 보유 종목 처리

정지 원인에 따라 보유 종목 처리가 달라진다. 어떤 경우든 정지 시 **현재 보유 종목 목록 + 평가손익**을 텔레그램으로 즉시 발송하여 수동 대응을 지원한다.

|정지 원인                         |보유 종목 처리                                 |
|------------------------------|-----------------------------------------|
|연속 손절 N회 / 일손실 한도 도달          |전량 시장가 매도 시도. 매도 실패 종목은 목록 발송 후 수동 처리 요청 |
|API 연결 오류 3회 연속               |매도 불가 상태. 재연결 대기. 복구 즉시 현재가/손절 조건 점검 후 처리|
|포지션 불일치 감지                    |sync_mode 설정에 따라 처리 (자동 싱크 or 수동 확인)     |
|수동 정지 — 진입 중단 (`/pause entry`)|신규 매수 시그널만 차단. 보유 포지션 손절/익절 모니터링은 계속     |
|수동 정지 — 전체 중단 (`/pause all`)  |신규 진입 + 자동 청산 모두 중단. 비상 스위치. 포지션은 수동 처리  |


> **시스템 정지 시 전량 청산:** 연속 손절 / 일손실 한도 도달 등 전량 청산이 필요한 경우, `margin_close_priority` 순서 그대로 전체 포지션을 빠짐없이 청산한다. 15:20 루틴과 달리 자기 자금 기준으로 중간에 멈추지 않고 끝까지 진행한다.
> 
> **재가동 시 복구 루틴:** `/resume` 명령 수신 시 즉시 실제 계좌 포지션을 조회하여 시스템 내부 상태와 동기화한 뒤 루프 재시작.

## 9. 백테스트 엔진

### 9.1 합격 기준 (실계좌 진입 전 반드시 통과)

|지표          |최소 기준 |
|------------|------|
|샘플 외 승률     |≥ 52% |
|Sharpe Ratio|≥ 1.0 |
|최대 낙폭 (MDD) |≤ 15% |
|수수료 포함 기대값  |> 0   |
|백테스트 샘플 수   |≥ 200건|

### 9.2 검증 방법

- **워크포워드:** 훈련 80% / 검증 20% 분리, 검증 성과 붕괴 시 과적합 플래그
- **몬테카를로:** 거래 결과 무작위 재배열 1,000회 → 최악 드로우다운 분포 확인
- **재최적화 주기:** 루프 C(30분 주기)에서 파라미터 재검토, 성과 악화 시 플래그 후 수동 확인

### 9.3 백테스트 실행 시점

백테스트는 두 가지 경로로 실행된다.

|실행 경로       |설명                                              |
|------------|------------------------------------------------|
|**정기 자동 실행**|루프 C에서 주 1회(예: 일요일 새벽) 자동 실행. 전략 파라미터 재최적화 결과 반영|
|**수동 실행**   |웹 대시보드에서 기간 / 전략 / 파라미터를 지정하여 요청                |

백테스트는 무거운 작업이므로 비동기로 실행한다. 요청 즉시 작업 ID를 반환하고, 완료 시 대시보드 자동 갱신 + 텔레그램 알림으로 결과를 전달한다. 실행 중인 백테스트는 대시보드에서 진행률을 확인할 수 있다.

## 10. 미수 거래

### 10.1 기본 정책

단기 전략의 레버리지 효과를 위해 미수 거래를 지원한다. 미수는 당일 미상환 시 반대매매가 발생하므로 15:20에 계좌 전체 포지션이 자기 자금을 초과하는지 확인하고, 초과분이 있을 때만 필요한 만큼만 청산한다. 장중 포지션 청산으로 미수가 자연 해소된 경우에는 추가 강제 청산 없이 잔여 포지션을 오버나이트로 유지할 수 있다.

### 10.2 미수 설정값

ConfigManager를 통해 관리.

|파라미터                   |기본값            |설명                                         |
|-----------------------|---------------|-------------------------------------------|
|`margin_ratio`         |1.5            |미수 배율 (하드캡 2.5, 초과 불가)                     |
|`margin_close_time`    |15:20          |미수 강제 청산 루틴 실행 시각                          |
|`margin_close_priority`|[1, 2, 3, 5, 4]|강제 청산 시 전략별 청산 순번. 앞 번호부터 청산. 웹UI에서만 변경 가능.|

### 10.3 미수 운영 규칙

- **15:20 강제 청산 루틴:** 계좌 전체 포지션 평가금액이 `daily_base_capital`을 초과하는 경우에만 실행. `margin_close_priority` 순서대로 포지션을 1개씩 청산하면서 매번 전체 포지션을 재계산, 자기 자금 이하로 내려오는 순간 중단. 기본 설정(`[1,2,3,5,4]`)에서 전략4 포지션은 다른 전략 포지션이 모두 청산되어도 미수가 남아있는 경우에만 청산된다.
- **시스템 정지 시 전량 청산:** 연속 손절 / 일손실 한도 도달 등 전량 청산이 필요한 경우, `margin_close_priority` 순서 그대로 전체 포지션을 끝까지 청산한다 (7.1절 참고).
- **손실 한도 계산:** 일일 손실 한도는 미수 레버리지를 반영한 실제 손실 기준으로 계산 (예: 1.5배 미수 포지션 1% 하락 = 실손실 1.5%)
- **미수 가능 여부 확인:** 주문 전 키움 API 잔고 조회로 미수 가능 금액 실시간 확인
- **NXT 구간 미수 금지:** NXT 프리/애프터마켓에서는 미수 진입 불가 (유동성 리스크)

## 12. 개발 로드맵

### 1단계 — 기반 구축 (1~2주)

- 키움 REST API 연결 및 인증
- ConfigManager 구현 (DB 연동, 설정값 검증, 변경 이력)
- 캔들 데이터 수집 모듈 (계층별 기간 대응, 증분 업데이트)
- PostgreSQL 스키마 설계 및 초기 데이터 적재
- 장 운영 시간별 스케줄러 (정규장 / NXT 분리)

### 2단계 — 백테스트 엔진 + 전략 구현 (2주)

- 백테스트 엔진 구축 (신호/진입 분리 구조 먼저)
- 전략 1~5 구현
- 수수료/슬리피지 강제 반영 검증
- 합격 기준 통과 여부 자동 판정

### 3단계 — 리스크 관리 + 텔레그램 (1주)

- 리스크 관리 모듈
- 텔레그램 봇 (알림 + 명령 처리)
- NXT 구간 별도 처리 및 포지션 상한 적용

### 4단계 — 페이퍼 트레이딩 (최소 2주)

증권사 모의투자 계정은 사용하지 않는다. API 제약으로 실제 시장과 동일한 환경을 만들 수 없기 때문이다. 대신 실계좌 API를 그대로 사용하면서 주문 실행 단계만 가상으로 처리하는 자체 구현 방식을 사용한다.

#### 페이퍼 트레이딩 구현 방식

**운영 모드 플래그**

환경 변수 `TRADING_MODE=paper | live` 로 모드를 구분한다. 코드 분기는 주문 실행 레이어 한 곳에만 집중하고, 데이터 수집/전략/리스크 체크는 두 모드에서 동일하게 동작한다.

```
[공통] 데이터 수집 → 전략 실행 → 리스크 체크 → 시그널 생성
                                                      ↓
                                          TRADING_MODE 분기
                                         ↙              ↘
                                    paper              live
                               가상 주문 처리       실제 API 주문
```

**가상 주문 처리 로직**

실제 체결은 발생하지 않지만, 체결 시뮬레이션은 최대한 보수적으로 처리한다.

|항목       |처리 방식                                           |
|---------|------------------------------------------------|
|진입가      |시그널 발생 봉의 다음 봉 시가 (N+1 시가)                      |
|손절/익절 체결가|해당 가격 도달 확인 후 즉시 체결 처리                          |
|수수료      |실계좌와 동일하게 차감 (매수 0.015% + 매도 0.015% + 거래세 0.18%)|
|슬리피지     |설정값만큼 불리한 방향으로 적용 (기본 0.05%)                    |
|미체결 처리   |지정가 시그널이 해당 봉 내 가격에 도달 못하면 미체결로 기록              |
|부분 체결    |초기에는 전량 체결로 단순화. 추후 유동성 기반 부분 체결 시뮬레이션 추가 가능    |

**가상 포트폴리오 관리**

별도 DB 테이블(`paper_portfolio`, `paper_orders`, `paper_trades`)에 가상 잔고와 거래 내역을 관리한다. 실계좌 테이블과 스키마를 동일하게 유지하여 모드 전환 시 코드 변경 없이 테이블만 교체.

```
초기 가상 자산 설정 (예: 1,000만 원)
  ↓
시그널 발생 → 가상 주문 생성 (paper_orders)
  ↓
다음 봉 시가에 체결 처리 → 포트폴리오 업데이트
  ↓
손절/익절 도달 시 청산 처리
  ↓
거래 기록 저장 (paper_trades)
```

**페이퍼 트레이딩 합격 기준**

아래 기준을 모두 통과해야 실계좌 연결을 허용한다. 시스템이 자동으로 판정하며, 미달 시 텔레그램으로 알림.

|지표          |기준                    |
|------------|----------------------|
|최소 시그널 수    |100건 이상               |
|운영 기간       |최소 2주 (단기 운 배제)       |
|승률          |≥ 52%                 |
|Sharpe Ratio|≥ 1.0                 |
|MDD         |≤ 15%                 |
|포지션 불일치 발생  |0건 (시스템 안정성 확인)       |
|오류율         |전체 루프 사이클 대비 오류 < 0.1%|

#### 실계좌 전환 절차

1. 페이퍼 합격 기준 통과 확인 (`/paper_report` 명령)
1. `TRADING_MODE=live` 로 환경 변수 변경
1. 컨테이너 재시작

### 5단계 — 실계좌 연결

- 소액 (총 자산의 10% 이하)으로 시작
- 2주 검증 후 점진적 증액
- 백테스트 vs 페이퍼 vs 실전 성과 괴리 지속 모니터링

## 13. 로깅

외부 API 연동이 시스템의 대부분을 차지하므로 장애 발생 시 정확한 추적을 위해 촘촘한 로깅이 필수다.

### 13.1 로그 레벨 정의

|레벨        |용도          |예시                              |
|----------|------------|--------------------------------|
|`DEBUG`   |개발 중 상세 추적  |API 요청/응답 원문, 루프 사이클 상세         |
|`INFO`    |정상 흐름 기록    |진입/청산 실행, 캔들 수집 완료, 설정 변경, 토큰 갱신|
|`WARNING` |비정상이지만 계속 진행|API 재시도, 시그널 포기(미체결), 토큰 만료 임박  |
|`ERROR`   |처리 실패       |주문 오류, 데이터 수집 실패, 재시도 소진        |
|`CRITICAL`|시스템 정지 수준   |인증 실패, 포지션 불일치, API 연결 두절       |

운영 중에는 `INFO` 이상만 출력. 디버깅 필요 시 ConfigManager에서 `log_level=DEBUG`로 변경.

### 13.2 구조화 로그 형식 (JSON)

```json
{
  "timestamp": "2026-03-31T09:05:02.123",
  "level": "INFO",
  "module": "order_executor",
  "event": "order_placed",
  "ticker": "005930",
  "strategy": "ema_pullback",
  "position_id": "pos_20260331_005930_ema",
  "order_type": "limit",
  "price": 75400,
  "quantity": 13,
  "elapsed_ms": 187
}
```

JSON 형식으로 남기면 이후 DB 적재나 분석 도구 연동이 용이하다.

### 13.3 필수 로깅 포인트

|포인트       |레벨                 |기록 내용                         |
|----------|-------------------|------------------------------|
|API 요청    |`DEBUG`            |엔드포인트, 파라미터, 응답 코드, 소요 시간     |
|API 재시도   |`WARNING`          |재시도 횟수, 오류 내용                 |
|토큰 갱신     |`INFO`             |갱신 시각, 새 만료 시각                |
|토큰 갱신 실패  |`CRITICAL`         |실패 횟수, 오류 내용                  |
|주문 실행     |`INFO`             |종목, 전략, 주문 유형, 가격, 수량         |
|주문 실패     |`ERROR`            |오류 코드, 재시도 여부                 |
|포지션 상태 전환 |`INFO`             |position_id, 이전 상태 → 새 상태, 체결가|
|포지션 불일치 감지|`CRITICAL`         |시스템 내부 상태 vs 실계좌 상태 비교        |
|설정 변경     |`INFO`             |변경 주체(텔레그램/웹UI), 키, 이전값, 새값   |
|시스템 정지/재가동|`CRITICAL` / `INFO`|사유, 보유 종목 목록                  |
|루프 사이클 이상 |`WARNING`          |사이클 소요 시간, 임계값 초과 여부          |

### 13.4 로그 저장 및 관리

- **파일 로그:** 일별 로테이션 (`trading_20260331.log`). Docker 볼륨에 마운트하여 컨테이너 재시작 후에도 보존
- **컨테이너 로그:** `docker logs`로 실시간 확인 가능
- **보관 기간:** 90일 (설정 가능)
- **로그 레벨 설정:** ConfigManager의 `log_level` 키로 런타임 변경 가능
